# Design: Swift, Kotlin, and Dart Generators

**Date:** 2026-09-11
**Status:** Approved for planning
**Sub-project:** 6 of 6 (see `docs/superpowers/specs/2026-09-10-core-engine-ts-generator-design.md` for the original decomposition; this is the last item on the original roadmap)

## Goal

Add three native mobile model generators — Swift `Codable` structs, Kotlin data classes, and Dart classes — completing the PRD's stated target list (`TypeScript`, `Zod`, `Swift`, `Kotlin`, `Dart`). All three plug into the existing `ir.Document` with no changes to `internal/spec` or `internal/ir`, following the exact architectural pattern the Zod generator (sub-project 3a) established: a new `internal/gen/<lang>` package, a `Generate<Lang>`/`<Lang>Options` pair in `pkg/engine`, and a new `--target` value in `internal/cli`.

Treated as one combined sub-project rather than three, since all three share the same IR-driven architecture and most of the same design questions (nullability folding, field naming, cyclic handling, output modes) — the differences are per-language specifics within a shared shape, not three independent efforts.

## Nullability: one axis instead of two

TS represents "optional" (`?:`, key may be absent) and "nullable" (`| null`, key present but `null`) as two independent, combinable pieces of syntax. Swift, Kotlin, and Dart each have exactly one optionality mechanism (`T?` vs `T`) — there is no separate way to express "always present but might be null" versus "might be absent." A field in all three languages is `T?` if the IR's `Field.Optional` **or** `Field.Nullable` is true, and plain `T` otherwise. This is a fact about the target languages, not a stylistic choice.

## Field naming: camelCase with explicit wire mapping

TS/Zod deliberately keep JSON field names verbatim as property names (`photo_urls`), since JS/TS object literals and interfaces accept any string as a key with no runtime cost. Swift/Kotlin/Dart properties are conventionally camelCase, and all three languages' standard style guides (and their linters) flag snake_case properties. This sub-project converts field names to camelCase (`photoUrls`) and emits an explicit mapping back to the real wire name so JSON still round-trips correctly:

- **Swift:** a `CodingKeys: String, CodingKey` enum mapping each camelCase case to its wire string, which `Codable` consults automatically during encode/decode.
- **Kotlin/Dart:** an explicit key string literal in the hand-written `fromJson`/`toJson` methods (see below) — no extra mechanism needed since that code is already being generated by hand.

## Cyclic models: only Swift needs special-casing

Swift structs cannot directly or indirectly contain themselves — the compiler rejects it as "value type has infinite size," the same class of problem sub-project 1 and 3a solved for TS/Zod. Per the established `Model.Cyclic` flag: non-cyclic models are Swift `struct`s (value semantics, matches the PRD's "Codable structs" framing); a model flagged `Cyclic` becomes a `class` instead, exactly mirroring how the Zod generator special-cases only the cyclic path rather than changing every model uniformly.

Kotlin and Dart have no equivalent problem: `data class`/class properties are always JVM/Dart object references, never embedded values, so a self-referencing data class or class compiles and behaves correctly with no special-casing at all.

## allOf: always flatten, never model inheritance

None of the three target languages has an inheritance mechanism that maps cleanly onto `allOf`'s "one or more base schemas plus own properties" shape the way TS's `interface X extends Y, Z` does:

- Swift structs cannot inherit from anything (only classes and protocols can, and protocols don't carry stored properties).
- Kotlin explicitly disallows one `data class` extending another (breaks `equals`/`hashCode`/`copy()` correctness guarantees the language relies on).
- Dart supports single inheritance (`extends`), but `allOf` can reference multiple base schemas, which a single `extends` clause can't represent anyway.

All three languages therefore always flatten: every field from every `allOf` member plus the schema's own properties becomes one combined field list on one struct/class, using the same flattened list `internal/ir`'s `buildAllOfNode` already computes. No inheritance relationship is modeled in the generated Swift/Kotlin/Dart code, even where the source schema's `allOf` conceptually reads as "extends."

## Enums: string-backed with an explicit value property

Each language gets a string-backed enum that preserves round-tripping to the exact wire value, since enum constant naming conventions (Swift lowerCamelCase cases, Kotlin/Dart's idiomatic UPPER_SNAKE_CASE-or-camelCase constants) don't always match the JSON string verbatim:

- **Swift:** `enum Status: String, Codable { case available, pending, sold }` — Swift's `String`-backed enums default each case's raw value to its own name, so this needs no extra machinery when the wire values are already valid Swift identifiers (the common case); a case whose wire value isn't a valid identifier gets an explicit raw-value string once sanitized, following the same identifier-sanitization approach already used elsewhere in the codebase.
- **Kotlin:** `enum class Status(val value: String) { AVAILABLE("available"), PENDING("pending"), SOLD("sold") }` plus a small companion lookup (`fromValue`) for decoding.
- **Dart:** an enhanced enum (Dart 2.17+) — `enum Status { available('available'), pending('pending'), sold('sold'); final String value; const Status(this.value); }` — with the same kind of lookup for decoding.

## oneOf/anyOf: deferred for all three mobile targets

TS represents a union natively (`type X = A | B`) and Zod via `z.union([...])`; none of the three target languages has an equivalent construct without generating a hand-rolled sum type (Swift enum-with-associated-values, Kotlin/Dart sealed class hierarchy) plus custom "try each variant" decode logic per language — real, substantial, language-specific work on top of everything else in this sub-project.

**Decision:** out of scope for this round. A model or field whose type is a union (`ir.KindUnion`) is skipped from Swift/Kotlin/Dart output with a clear comment explaining why, rather than generated as something incorrect. This is recorded as a follow-up in `docs/superpowers/specs/2026-09-10-future-considerations.md`, the same way OpenAPI 3.1 and paths/operations typing were deferred earlier in this project.

## JSON approach per language

- **Swift:** `Codable` conformance — free, standard-library JSON support. No dependency, no generated boilerplate beyond the `CodingKeys` enum where field names were renamed.
- **Kotlin:** no built-in reflection-based JSON exists in the language or standard library. Rather than requiring the consuming project to add `kotlinx-serialization-json` and apply its compiler plugin (a real Gradle-level ask, much heavier than "npm install zod"), generated data classes get hand-written `fun toJson(): Map<String, Any?>` and `companion object { fun fromJson(json: Map<String, Any?>): X }` methods, using only the Kotlin standard library.
- **Dart:** in the identical position to Kotlin (no built-in reflection-based JSON), for the identical reason: hand-written `Map<String, dynamic> toJson()` and `factory X.fromJson(Map<String, dynamic> json)`, no dependency.

Both Kotlin's and Dart's hand-written approach produces more generated code per model than an annotation-based approach would, but matches this project's established "immediately usable, zero extra consumer setup" precedent from TS and Zod.

## Output modes

Both modular (one file per model, plus per-language conventions — e.g. `Pet.swift`, `Pet.kt`, `pet.dart`) and monolithic (single file via `--out-file`) are supported, mirroring the existing `TSOptions{Modular}`/`ZodOptions{Modular}` pattern exactly. No package or namespace declaration is emitted by default in any of the three (Kotlin compiles into the root package with no statement; Dart and Swift need none) — keeps output usable with zero configuration; a `--package`-style flag is a reasonable future addition but isn't needed for this round.

## CLI wiring

`swift`, `kotlin`, and `dart` become three more valid `--target` values, each accepted one at a time exactly like `ts` and `zod` are today. Comma-separated multi-target generation (`--target ts,zod,swift`) — documented in `Claude.md`'s architecture notes but never actually implemented, even for the existing `ts`/`zod` pair — stays out of scope for this sub-project; it's a self-contained CLI enhancement independent of adding more generators; a follow-up note goes into `future-considerations.md`.

## Testing

Golden-file tests for all three, following the exact pattern established in sub-projects 1 and 3a. This environment has `swiftc` installed but not `kotlinc` or `dart`, so:

- **Swift** gets an opt-in real-compilation verification test (mirroring `pkg/engine/golden_zod_typecheck_test.go`'s `tsc` check) that actually invokes `swiftc` against generated golden output. This pattern caught every Critical bug found in the Zod and WASM sub-projects, and it's runnable in this environment.
- **Kotlin** and **Dart** get the equivalent opt-in tests (`kotlinc`/`dart analyze` against generated output), structured to skip cleanly wherever the toolchain isn't installed — including in this environment, where they won't run today but will for anyone with those toolchains present.

## Addendum: inline (field-level) enums

Discovered while writing the implementation plan, not covered above: TS/Zod render an enum declared directly on a field (not as its own top-level schema — e.g. `petstore.yaml`'s `status` field) as an inline literal-union type, needing no separate declaration. Swift/Kotlin/Dart enums must be named, separately-declared types, so this needs its own decision.

**Decision:** synthesize a new top-level named type for each inline enum, named `<ModelName><FieldNameCapitalized>` (e.g. `Pet`'s `status` field becomes a top-level `PetStatus` enum, generated alongside `Pet`). This keeps full type-safety and feature parity with TS/Zod, at the cost of the renderer needing to accumulate extra top-level declarations as a side effect of rendering a model's fields, not just return a type-string for each field the way TS/Zod's renderers do.

The same synthesized-name convention applies uniformly across all three languages, so a spec generating multiple mobile targets gets a consistently-named `PetStatus` type in each.

**Generalization, same root cause:** the identical problem exists for an inline (non-`$ref`) nested *object* on a field — TS/Zod render it as an anonymous inline object-literal type, which none of the three mobile languages can express either. This gets the identical fix, for the identical reason (feature parity, already decided above): a field whose type is a `KindObject` not reached through a `$ref` also gets a synthesized top-level name (`<ModelName><FieldNamePascalCase>`), recursively — a nested object inside that synthesized type follows the same rule with its own name appended (e.g. `PetAddressCity`). An inline enum/object inside an array's items uses the same suggested name as the field itself (the array wrapper doesn't change the naming).

**The complete, consistent rule set this settles on**, covering every IR node kind a field can resolve to:
- `KindRef`, `KindPrimitive` (except `PrimitiveUnknown`), `KindArray`: render directly, exactly as before.
- `KindEnum` or `KindObject` reached directly (not through a `$ref`): synthesize a named top-level type as above.
- `KindUnion`, `KindIntersection` (the allOf-with-non-object-member fallback), and `PrimitiveUnknown`: none has a clean, correct representation in any of the three languages. Skip with a comment explaining why — at the **model** level (the whole model is omitted from output, generation continues for the rest of the document, matching the oneOf/anyOf deferral above) when it's the model's own top-level type, or at the **field** level (that one field is omitted from the struct/class, with a comment, generation continues for the model's other fields) when it occurs nested inside an otherwise-representable model.

## Explicitly out of scope

- oneOf/anyOf support for Swift/Kotlin/Dart (see above — deferred, recorded in `future-considerations.md`).
- Comma-separated multi-target CLI support (see above — deferred, recorded in `future-considerations.md`).
- Any `--package`/namespace-configuration flag.
- Any change to `internal/spec`, `internal/ir`, `internal/gen/ts`, `internal/gen/zod`, or the WASM build — this sub-project only adds new generator packages and wires them into `pkg/engine`/`internal/cli`.
- The web playground (`web/`) gaining Swift/Kotlin/Dart as selectable targets — the playground's design (sub-project 5) explicitly scoped its target picker to `ts`/`zod`; extending it is a separate, small follow-up if wanted later.
